# Example sources and assumptions

`examples/rollups.json` holds six well-known Ethereum rollups. Its facts come
from a **historical L2BEAT-derived snapshot dated 2026-10-27**, supplied with the
task that created this example. They are a dated snapshot, not a live
assessment: L2BEAT's data and the rollups themselves change, so check the
project pages below before relying on any value.

## Provenance

- **Supplied facts.** Every field value in `examples/rollups.json` was taken as
  given from the supplied snapshot. None was re-derived from on-chain state or
  re-checked against L2BEAT for this example.
- **Independently corroborated claims.** None. The links below point to the
  public L2BEAT pages the snapshot is modeled on, but no value here was checked
  against them when the example was written. Treat every value as supplied.
- **Derived outputs.** `examples/expected.txt` and `examples/expected.json` were
  generated by running this repository's CLI on the input
  (`node src/cli.ts examples/rollups.json` and
  `node src/cli.ts --json examples/rollups.json`). `test/examples.test.ts`
  checks that both stay byte-identical to the CLI output.

## How each field was mapped

- `name`: the project's display name on L2BEAT.
- `stage`: the L2BEAT stage (0, 1 or 2) in the snapshot.
- `proofSystem`: `fraud` for live fraud or fault proofs (optimistic rollups),
  `validity` for live validity (ZK) proofs. No row uses `none`.
- `permissionlessProving`: `true` only where anyone can submit or challenge
  state proposals in the snapshot (the three optimistic rollups). The three ZK
  rollups have whitelisted provers, so `false`.
- `exitWindowDays`: the regular-path delay, in days, that users have to exit
  before an upgrade they disagree with takes effect. `0` means no exit window
  on that path.
- `upgrades`: `securityCouncil` with the council Safe's own signing threshold
  and member count; `multisig` for a non-council team multisig.
- `dataAvailability`: all six post data to Ethereum as blobs, so
  `ethereumBlobs`.
- `forceInclusion`: `true` only where a user can force a transaction into the
  chain without operator cooperation if the sequencer censors them.

## Modeling caveats

- **Exit windows are regular-path values.** All six rollups also have an
  emergency upgrade path with no exit window. The model scores only the regular
  path.
- **Council thresholds describe the council Safe alone.** Any other required
  co-signers in the upgrade path are left out of `threshold` and `members`.
- **Base's proof label is simplified.** The snapshot describes Base's system as
  a hybrid of TEE and ZK proving, and the brief calls this a "validity label".
  The supplied row nevertheless gives `proofSystem: "fraud"` with
  permissionless proving, and the stated score of 70 depends on that row. The
  example keeps the row as supplied. Either live label earns the same 20 points
  in this rubric, so the score would not change, but the label does not capture
  the hybrid design.
- **Scroll** is upgraded by a 3-of-4 team multisig, which the input shape
  records only as `multisig`. Its operators can disable enforced batches, so its
  `forceInclusion: true` is conditional.
- **ZKsync Era's priority queue does not count as force inclusion**, so
  `forceInclusion` is `false`.
- **Starknet's council minority does not count as force inclusion.** A council
  minority's ability to step in does not let an ordinary user force a
  transaction, so `forceInclusion` is `false`.
- The score is a transparent heuristic, not a probability of loss or a safety
  certification. It leaves out implementation bugs, how independent council
  members really are, detailed upgrade powers and force-inclusion delays.
